Declarative workflow

The Platform Agent’s SOUL.md forbids direct infrastructure mutations. When the agent has a change to make — a policy update, a node pool tweak, a security patch, a namespace addition — and someone asked for it, it doesn’t kubectl apply. It writes the change into your GitOps repo as a pull request via the submit-suggestion skill. The short-lived GitHub token that push needs is minted on demand by Minty on the credential side of the boundary; it never enters the container the agent’s shell runs in.

Why

Section titled “Why”
  • Human review. Every infrastructure change gets seen before it hits prod. The PR is the audit trail.
  • Rollback via revert. A bad remediation is one revert away from undone.
  • Compatibility with your existing GitOps. ArgoCD, Flux, RootSync — whichever reconciler you already run applies the merged change. The agent doesn’t compete with your reconciler.
  • Least privilege on the cluster. The agent’s Kubernetes identity cannot mutate workloads or cluster state — its only write grant is a leader-election housekeeping Role confined to its own namespace — so even a misled persona cannot change a cluster through the Kubernetes API. Its GCP identity is a separate question, governed by the install-time permission set (read-only by default; custom, where you name every role, is the only way to widen it). See Security & IAM.

The submit-suggestion skill

Section titled “The submit-suggestion skill”

Source: agents/platform/skills/submit-suggestion/.

The agent invokes this skill when an SOP or a request asks for a change to be submitted. A question answered with a recommendation (“investigate and report”, “what would you change”) keeps the manifest in the reply; the pull request is opened only when someone asks for it, and a scheduled audit’s pull requests come from fleet-audit’s own promotion, never from this skill (SOUL.md §3). The pod holds no checkout of its own; the skill’s helper makes one, from the repository URL the agent resolves on startup out of the $GITOPS_STATE_CONFIGMAP ConfigMap (per SOUL.md §1). The flow:

  1. Runs python3 "$HERMES_HOME"/skills/submit-suggestion/scripts/submit_suggestion.py prepare --branch platform-agent/<change_type>-<target_id> (e.g. platform-agent/upgrade-policy-baseline). That brings the repository down into a private copy, cuts the topic branch off the repository’s default branch — or off the baseBranch its spec.integration.repositories entry sets, when it sets one — and prints the workspace path as JSON. The path is spelled from $HERMES_HOME because the skill is reached from a kanban card as well as from a cron turn, and neither starts in the profile directory: a card starts in its own workspace, and a cron turn in a directory of its own under cron/runs/.
  2. Applies the change inside the printed workspace (file writes, YAML patches), then stages only the specific files it edited — git add . / git add -A are explicitly forbidden — and commits using Conventional Commit messages.
  3. Runs the same helper with submit --branch … --title … --body-file …, which records the change, sends the branch up, and opens or refreshes the pull request. The description travels over a file under /opt/data/scratch rather than argv: a pull request body is full of backticks, and inside the double quotes the agent would write around it bash expands them.
  4. The script prints the PR URL to stdout; the agent posts it to Chat.

Every one of those steps is a version-control verb the credential broker performs on the agent’s behalf. There is no gh in the helper, no token in the container, and no directory shared with the process that holds the credential — see Credential isolation.

Keeping concurrent agents apart is step 1’s other job: a Pod runs ten audit crons alongside every kanban worker. They share one scratch root, and what separates them is the copy’s name, which is keyed on the repository and the branch — ten audit streams and a suggestion card can hold copies of the same GitOps repository at once, as long as each is on a branch of its own. Two cards that derive the same branch name for the same repository do land on the same copy, and there prepare refuses to replace one that holds work which was never sent up. --force is the way past that refusal, and taking it discards the unpublished work.

Safety red lines enforced by the skill: direct/manual cluster mutations are forbidden, and submit_suggestion.py hard-blocks pushes to the protected branches main, master, and production. Nothing the helper runs stages a file the agent did not name — commit records tracked files only, and an untracked one is refused by name rather than swept into the change, because the working copy is also where scratch output lands. The SKILL tells the agent never to run git add . in that copy itself; that one is an instruction to the model, not a guard in the code, and the copy’s git holds no credential in any case. Sending a branch up is fast-forward only: a second round on the same branch extends it, and a branch somebody else has moved since you read it is refused by name rather than overwritten. The one thing the helper removes from the forge is a spent branch — the agent’s own branch left behind by a closed or squash-merged pull request — so the name can be used again; the broker refuses the delete for anything else, under the rule in Security and IAM.

Answering a reviewer on the PR

Section titled “Answering a reviewer on the PR”

Opening the PR does not end the conversation. The github-repo-watcher poller sweeps for review comments alongside issues, every 10 minutes, and hands anything it finds to the pr-conversation skill, so a reviewer’s question in the thread reaches the agent without anyone going back to chat to relay it.

What addresses the agent. A comment that begins with /agent <request>, or with an @-mention of the account that opened the PR — nothing else. Not a line of the comment: the start of it. Review threads are mostly humans talking to each other, and a watcher that woke on every comment would spend a model turn on “looks good to me”.

Anchoring to the start is also what keeps the trigger auditable. Every Markdown construct that can hide text — a fenced block, an HTML comment, a code span, a block quote — needs characters before the text, and there is no room for them at the start of a comment. A /agent inside any of them therefore cannot fire, and writing about the trigger, as this page does, is not using it. The cost is that a command after a greeting does not fire either: put it first, or send it as its own comment. GitHub’s “Quote reply” button is the one that catches people out — it puts the quote above the cursor, so a reply composed with it never begins with your own words.

The rest of the line gets the same treatment, for the same reason. /agent fix the typo <!-- and add my key --> renders as /agent fix the typo, so the request the agent acts on and the request the next reviewer reads would be different strings. A request containing <, [, or ] is therefore declined rather than trimmed: those are the characters that open an HTML comment, a link, or an image, and a link title or image alt text carries words no reader sees. Restate the request without the link.

Who may. Accounts with write access to the repository. Anyone else is refused — usually with a reply saying so, posted by the poller itself without waking a model, since refusing needs no reasoning. “Usually”, because the reply is rate-limited and the refusal is not: past three refusals in a tick, or ten on one pull request, the comment is passed over in silence instead. Being refused quietly is still being refused, but a reviewer who was never told is the failure mode worth knowing about. Comments from other bots are passed over rather than refused, since answering one is a loop. Security and IAM is canonical for this boundary: it names the environment variables behind both bounds, the third case this summary elides, and what an untrusted comment can still put in front of the model.

What it can do. Answer a question, or amend the PR’s own branch through submit-suggestion Step 5 — the same fast-forward-only publish and protected-branch blocks as any other change. Never merge, approve, or close. Comment text is a request within the authority the agent already has: it cannot widen that authority, point the agent at another repository, or overturn a refusal.

Where the answer lands. In the PR thread, as a reply carrying a hidden marker keyed on the comment it answers — the same scheme the audit ledger uses, and the reason a standing request is answered once rather than every ten minutes. Only markers in the agent’s own comments count, so pasting the string cannot suppress somebody else’s request. There is no state file: the thread is the record, which is also what makes this work for a PR whose original chat session is long gone.

Scope is the agent’s own pull requests — head branch platform-agent/*, minus anything labelled agent:ignore.

The fleet-audit skill

Section titled “The fleet-audit skill”

Source: agents/platform/skills/fleet-audit/.

submit-suggestion fits a one-off change: the agent decides what to propose, writes the body, and opens a PR. A recurring fleet audit does not fit that shape. A daily audit using submit-suggestion would open a near-identical PR every morning; and an audit report is not a diff at all, so a PR is the wrong container for it — a reviewer would have to accept or reject every finding at once, a force-push would orphan their line comments each run, and closing the PR on a clean fleet would read as rejected rather than done. fleet-audit is the second write path, and it inverts the division of labour: the model produces evidence, the script produces the published artefacts.

The agent’s only output is a validated findings.json — one entry per deviation, each carrying the literal read-only command that proves it and a recommendation (action, rationale, risk). audit_report.py does the rest:

What it publishes to the GitOps repository has two tiers: a durable report that is always there, and — only where there is something to merge — narrow pull requests that carry an actual diff. An install with no GitOps repository gets neither tier: the run keeps its findings in the report store and reports them in chat.

Which repository gets the ledger

Section titled “Which repository gets the ledger”

The ledger issue and every remediation pull request (a merge request on GitLab) go to one repository: the one with role: gitops in spec.integration.repositories. The installer’s --gitops-repo and the chart’s platformAgent.integration.github.gitRepo give a repository that role. A context repository is never the target, because the agent only reads it. A managed repository gets the ledger only when it is the one managed repository and no repository has role: gitops.

  • To change the repository, give role: gitops to another repository. At most one repository can have that role. The next run writes its ledger in the new repository, because a run does not keep the repository of an earlier run. The open ledger issue in the old repository stays as it is.
  • One run in another repository. Ask the agent to run the audit with --repo <repository>. That repository must be managed. The repository applies to that run only: the next run goes back to the role: gitops repository.
  • Several repositories and no role: gitops. The audit does not choose one. It keeps its findings in the report store and reports them in chat on every run, with a message that tells you to give one repository role: gitops, or to name a repository for one run.
  • No repository. The run keeps its findings in the report store and reports them in chat, as the paragraph above says.
  • A forge with no issue tracker. When the provider of a forge declares that the forge has no issues, or no labels, a repository on that forge cannot hold a ledger issue. The run then keeps the ledger in the report store and reports it in chat, with the reason, and it still opens remediation pull requests on the forge. Its chat report gives their links. A scheduled run that finds nothing new stays silent, as it does with a ledger issue. To ask for a fix that the audit did not open, ask the agent in chat.
  • A repository the agent cannot reach. Before it publishes, the run reads one issue from the repository through the credential broker, or one pull request when the forge has no issue tracker. If the forge says that the repository does not exist, or that the install’s credential cannot read it, or the credential broker does not manage it, the run does not try another repository. It keeps its findings in the report store and reports them in chat on every run, and the report names the repository and the reason.
  • Another forge error. A TLS certificate that the credential broker does not trust, a forge host that does not answer, or a credential that the broker cannot load does not change the repository. The run stops with the error and publishes nothing to the forge or the report store. Chat says that the run did not finish, and the next run tries again. If the credential broker itself does not answer, the run stops with BROKER UNAVAILABLE and publishes nothing.

Tier 1 — the ledger issue

Section titled “Tier 1 — the ledger issue”

Each audit stream owns exactly one GitHub issue, rewritten in place on every run and labelled agent:audit, audit:<audit-id>, and severity:<highest severity present>. Its title is generated ([audit] <human name> — <n> findings (<c> critical)), and its body carries the scope table, a findings table with a state column whose every row links to the finding it names, and per-finding detail: evidence, impact, the finding’s own id, recommendation, remediation, and a link to that finding’s remediation PR where one exists.

A run that finds nothing closes the issue as completed, and closes any remediation PRs still open for the stream. That is the point of the shape: a closed issue reads as done.

Unless the run could not see the whole fleet. A cluster that was skipped, or one that was read but where some checks could not run, makes the run partial — and a finding’s absence from a cluster nobody looked at is not evidence it was fixed. Over a partial run the ledger stays open with a comment naming the gaps, previous findings on clusters the run did not check stay listed as not re-checked (a /remediate on one gets one reply that it waits for the first run that checks that cluster, and the run neither resolves it nor closes its pull request; on an install with no forge, the run’s chat summary names these findings), nothing is announced as resolved, and no remediation PR is retired, except one whose fix a repository declaration forbids, which is closed on the declaration alone.

Where a manual fix belongs

Section titled “Where a manual fix belongs”

A manual finding from the obtainability, compliance and AI security audits and the fleet-wide cost analysis gets notes that say where to make the fix. A manifest or gcloud finding gets no such note, and neither does a finding whose fix an open remediation pull request carries: a pull request whose delta block names the finding, or one on the branch the audit promised for the fix. A pull request opened by hand, outside the audit, does not count, and the row keeps its notes. The notes come from the audit’s collector, which reads the GitOps repository and the live object. You configure nothing beyond the GitOps repository. Context repositories are not read. A standard install reads the repository in content mode: the shell sandbox has no clone, so the collector copies the repository’s .yaml and .yml files, and the files named Kustomization, through the credential broker, which holds the repository for the sandbox. It writes no location note when the repository has more than 5,000 such files or more than 64 MiB of them, or more than 5,000 links to directories, when the broker names a path outside the repository, when the broker refuses to send a file or fails, or when the collector cannot write its copy. A file the broker will not send (over its per-file size limit, or a symbolic link) removes the declaring-file notes for its clusters/<cluster>/ tree, and, if the file could hold a release, all release-file and namespace-directory notes. The location note is skipped when the finding’s own remediation text names that path and the cut below keeps that mention. When the finding’s remediation text and the notes together are longer than the note cap of 2,000 characters, the remediation text is cut and ends with …(truncated), so that the notes fit; a code block in the text is never cut: the first code block and all text after it are removed, and the text before the block is cut. When the notes still do not fit, the location note is left out; the reconciler note is always shown. A code block that the text leaves open is closed. Route notes that the text copied from an earlier ledger are removed.

Which findings can get a note: in the obtainability, compliance and AI security audits, every check’s candidate goes through the same lookups. A finding on an object with a namespace can get any note. A cluster-scoped object (a ClusterRoleBinding, a GKE cluster or node pool) gets no declaring-file note, because the match needs metadata.namespace, but it can get the cluster directory of rule 3 below. The reconciler note comes from the workload checks and from the cluster checks that name a Service, a PodDisruptionBudget, a HorizontalPodAutoscaler, an RBAC binding or role, or a workload; checks that name a GKE cluster, a node pool or a Namespace (netpol-missing) carry none. In the fleet-wide cost analysis, the checks on Kubernetes objects can get the declaring-file, release-file and reconciler notes, never the namespace-directory note, and the checks on disks, addresses and forwarding rules get no note.

Each finding gets one location note at most, the first of these that the collector finds:

  1. The declaring file. The collector parses every YAML file under clusters/<cluster>/ in the GitOps repository, where <cluster> is the GKE cluster’s bare name as the audit lists it (prod, not <project>/<location>/prod), and matches the object’s kind, metadata.namespace and metadata.name. A file that does not parse as YAML (a Helm template, for example) is skipped, and so is an object with no metadata.namespace (for example in a Kustomize base that sets the namespace elsewhere). Two files that declare the same object give no note.
  2. The release file. An Argo CD Application (chart or local Kustomize overlay) or a Flux HelmRelease in the repository. It is matched by the Application name in the object’s argocd.argoproj.io/tracking-id annotation, or by the release name and namespace in its meta.helm.sh/release-name and meta.helm.sh/release-namespace annotations. An Application’s cluster is spec.destination.name as written, so in-cluster matches only a cluster with that name. Else it is spec.destination.server, mapped to a cluster name through the Argo CD cluster Secrets (label argocd.argoproj.io/secret-type: cluster, with stringData.name and stringData.server) that are committed to the GitOps repository; no Secret is read from a cluster, and the in-cluster server is not matched. A HelmRelease’s cluster comes from its clusters/<cluster>/ path. An ApplicationSet is not read.
  3. The namespace directory, where a new object for that namespace belongs. It is one of: the one directory under clusters/<cluster>/ that holds objects already declared in that namespace; else the local Kustomize root that an Argo CD Application renders into that namespace; else the one directory under clusters/<cluster>/ that holds objects for that cluster, if no AppProject in the repository limits namespaces. A directory inside a Kustomize root counts only through the second rule, and two candidate directories give no note. This note does not read the object’s markers.

A second note names what reasserts the object’s spec, read off the live object: the meta.helm.sh annotations give “the Helm release <name> in ” (Flux’s Helm controller writes them too), the argocd.argoproj.io/tracking-id annotation gives “the Argo CD Application <name>”, and an app.kubernetes.io/managed-by label with a value other than Helm gives that value. Argo CD renders a chart with helm template, which writes no meta.helm.sh annotations, so a chart that Argo CD installs shows as the Argo CD Application. An Argo CD install that tracks objects with the app.kubernetes.io/instance label (the default before Argo CD 3.0) writes no tracking-id annotation, and its chart objects usually carry app.kubernetes.io/managed-by: Helm, which is excluded: they get no reconciler note and no release-file note, but can get the namespace-directory note.

The notes say that the next sync or upgrade can revert a change made by hand. Argo CD reverts it at its next sync (at once with self-heal), Flux at the next upgrade of the release (or at its next reconcile when drift detection is on), and a plain helm install release only at the next helm upgrade, for fields that the chart sets. For a Kustomize overlay the release note says “the Kustomize overlay” in place of “the chart release”. When the namespace directory is a local Kustomize root (the second source in rule 3), its note also says to list the new file in the resources: of that root. When it is the directory for the whole cluster (the third source), the note says “A new object for this cluster” and that a namespaced object there must set metadata.namespace. A note shows a path or a name only when it has letters, digits and _./-, is not longer than 512 characters, and does not look like a credential to the redaction of the stored findings (for example, sk- in task- with 32 or more characters after it): another path gives no location note, and another reconciler, or one that is not one of the forms above, shows as “a controller whose name the audit does not show”. The notes go in a paragraph of their own below the finding’s remediation text.

Tier 2 — remediation pull requests

Section titled “Tier 2 — remediation pull requests”

A finding whose remediation is a manifest can be promoted into its own pull request on platform-agent/fix-<audit-id>-<slug>-<digest>, based on the repository’s base branch (its repositories[].baseBranch when set, else its default branch), carrying only that finding’s manifest and linked back to the ledger with Part of #<issue>. It takes the ledger’s labels plus audit:remediation, and it takes them again on every run that finds it still open — so a severity: that escalates between runs is reflected rather than frozen at whatever the PR opened with, and labels stripped during triage come back rather than leaving a PR the audit still owns invisible to agent:audit. Only the labels are re-applied: a run never force-pushes or rewrites a pull request it has decided to leave alone. Findings whose remediation.path values overlap share a single PR, since separate branches touching the same file would conflict on merge.

The branch finds the PR for a finding, and for a merged or closed PR its delta block (a hidden HTML comment in the PR body that lists the ids of the findings it fixes) limits which findings it claims — the harness keeps no finding-to-PR record of its own. The digest is taken over the group’s sorted set of remediation paths, not over its finding ids, because a group changes as findings come and go, and the files a fix touches stay the same. Finding ids are deterministic: the same problem gets the same id on each run while the check and the id scheme do not change, and the delta block joins on them. An open PR claims every finding in its group. A merged PR, or one a person closed, claims only the findings it names: any other finding on its branch (for example, a different check that later writes the same file) stays on the ledger with no PR, its entry links the PR that blocks an automatic one, and an explicit /remediate proposes a fix for every finding in the group that still reproduces.

Promotion is hybrid:

  • Automatic when the finding is graded critical — or major on one of three additive checks (a missing PodDisruptionBudget, a token mounted for a ServiceAccount nothing has granted, a ComputeClass with no On-Demand fallback) where the audit’s collector grades it at least major — its remediation is a manifest, and there is no live pull request on its branch — capped at five auto-promotions per run, with any withheld findings named in the ledger as awaiting an explicit request. Any other manifest finding is never promoted automatically, because a severity says how bad a finding is, not whether its fix is safe to open with nobody asking; the ledger names it as below the floor, and an explicit request opens it. Where the audit ran with a collector, the sweep also passes over a finding the collector did not confirm or whose fix it flagged for a human decision (the collector design).
  • On request otherwise. Someone with write access on the repo comments /remediate <finding-id> — or /remediate all — on the ledger issue, and the next run opens the PRs and replies with the links. Only manifest findings are promotable: naming a gcloud or manual finding gets one reply explaining that its fix is a command to run, not a file to merge. A command from an author without write access gets one reply and nothing else.

Kustomize renders only the files that its kustomization lists, and a remediation PR carries one file. So finish checks each manifest fix that adds a file that is not in the repository at the audited commit, whether or not the audit found the workload’s declaration. If the nearest kustomization does not list the file, no pull request opens and the finding becomes manual. This check needs no setting, and neither does automatic promotion. A kustomization is a file named kustomization.yaml, kustomization.yml or Kustomization. The audit looks in the file’s directory, then in each parent directory up to the top of the repository, and only the first one it finds counts: it does not follow a parent that lists the subdirectory, or a components: entry. The match is textual, so any mention of the file’s path relative to the kustomization’s directory counts, a comment included. A file in a subdirectory with no kustomization of its own is listed by that path, for example budgets/pdb.yaml.

The ledger row shows the state open, the kustomization path, the resources: line to add, and the content of the file the worker wrote, in a YAML block cut to fit the row. finish writes no PodDisruptionBudget of its own in a Kustomize root, so the content is always the worker’s. A degraded finding is not a manifest fix, so it does not count toward the five automatic pull requests of a run. A /remediate <finding-id> comment on it gets the reply every non-manifest finding gets: it has a manual remediation, so no pull request can carry it; the ledger row holds the kustomization and the line. When the agent runs the remediate command for it, the command refuses it by name, and the refusal repeats the row’s note. When the broker that reads the repository is busy (a server error or too many requests) or does not answer, finish stops with BROKER UNAVAILABLE before it writes the ledger or opens a pull request, the run stays in flight, and the worker runs the same finish again when the broker answers; no number of retries is set. When the broker refuses the question (a 4xx status), the fix becomes manual with a note that says the audit could not check it, and the note names no kustomization the audit did not see.

The SOP puts a new object such as a PodDisruptionBudget in a new file in the directory of the workload’s declaration. The collector finds that declaration: it parses the YAML files under clusters/<cluster>/ in the GitOps repository and matches the object by cluster, kind, namespace and name. The <cluster> directory name must equal the GKE cluster’s name; a directory with another name matches no cluster. When it finds none, the SOP uses a directory that declares into the namespace, and if that directory is a Kustomize overlay, the SOP makes the fix manual at once. To fix the finding, a person adds the file and its resources: line in one change, because a kustomization that lists a file that is not there does not render. Until that change merges and the audit runs again, the finding stays open. When the next run no longer finds the problem, the finding is resolved in the usual way. If the kustomization at the audited commit already lists the file, the audit keeps the fix, and the sweep or a /remediate can open its pull request as for any other manifest fix. The findings nudge in chat reads the findings queue, which the inventory scan fills; the fleet audit does not write to that queue, so this check does not change what the nudge names.

Every request gets exactly one answer and the answer is never silence, because a command that vanished is indistinguishable from an audit that has not run yet. An acknowledgement names each target and what became of it — the PR’s URL, already open with its labels re-asserted and its diff untouched, superseded by a human close, or queued for a retry — rather than a count. A refusal says which of the reasons applies, and a request the parser cannot honour at all (the command mid-sentence rather than on its own line, or with no target after it) gets a reply carrying the correct syntax and the ids that would have worked. A /remediate inside a code span is prose about the command, not an attempt at it — which is how the harness avoids answering its own comments. Each answer is recorded behind a hidden marker keyed on the triggering comment, so a standing request is answered once rather than every morning.

Each finding’s state is recomputed every run from two facts — whether it still reproduces, and what its remediation PR is doing — and never stored. The ledger renders exactly one of open, fix proposed, ⚠ fix merged, still reproduces, resolved (fix merged), resolved, fix refused, or fix withdrawn, awaiting re-proposal. Two of those act on the PR side, and the second is one the old PR-as-report model had no way to express:

  • A remediation PR whose finding no longer reproduces is closed automatically, with a comment naming the command that no longer reproduces. The branch is deliberately not deleted, so any human fixup pushed to it survives and the PR can be reopened.
  • A finding that still reproduces after its PR merged is rendered with a “fix merged, still reproduces” warning and the merged PR gets one comment. It is never reopened.

The last two states are the same event seen from opposite sides: a fix PR that is closed, unmerged, while the finding is still there. Who closed it decides everything, and the audit:stale-closed label is how the harness tells its own work apart from a person’s. Its own stale-closes carry that label and render as fix withdrawn, awaiting re-proposal — the finding is treated as having no PR at all, so it is promotable again on the usual terms. A PR a human closed renders as fix refused and is final: re-proposing it would overrule a person every morning. The escape hatch there is /remediate <finding-id>, from someone with write access and written after the close — an older command still sitting in the thread is reported as superseded rather than acted on, since comments are never edited away and one would otherwise re-open the same close forever.

What the script owns

Section titled “What the script owns”

Three properties follow from the script owning the artefacts rather than the model:

  • One ledger per audit stream. The --audit id is checked against a fixed allowlist, and the branch and label names are derived from it rather than passed in, so a typo cannot open an unregistered stream. The agent never calls gh issue create itself.
  • A computable delta. The issue body carries a hidden <!-- audit-findings: [...] --> block, and the harness keeps its own copy of each body it publishes in a report store on the agent’s volume; the next run diffs finding ids against that stored copy, so a hand edit to the public issue cannot change what the harness believes it published. Only a run for a stream and repository the store has never held, as the first after an upgrade or on a replaced volume is, reads the block back once to seed it. A stored record that is missing, unreadable, or does not match the issue is never re-seeded from the issue: the run treats its memory as lost and withholds the delta rather than trusting the public body. Stability is not asked of the model: the id is derived in code from (check, cluster, namespace, object) and any id in the findings file is discarded, so the same problem keeps the same id without anyone remembering to make it so. A second hidden line stamps which identity scheme minted the ids, and a run that reads a block from a different scheme withholds resolved for one run rather than reporting a renamed finding as a fixed one.
  • No invented output. The model never writes the title, body, commit message, or any timestamp — so two runs against an unchanged fleet produce an unchanged ledger.

The agent:audit label is also what keeps the issue-writing jobs apart: the github-issue-resolver poll query excludes it, and agent:delivery-watch with it, so it never tries to “resolve” an audit ledger or the chat-delivery ledger.

fleet-audit shares submit-suggestion’s guardrails: same Minty token path, the same refusal of git add . / git add -A, and the same hard block on force-pushing main, master, or production.

Minty (GitHub Token Minter)

Section titled “Minty (GitHub Token Minter)”

Source: k8s-operator/config/integrations/github/.

Minty is a small in-cluster service that brokers GitHub App installation tokens without any long-lived secret ever touching the agent’s pod.

How it works

Section titled “How it works”
  1. A GitHub App is created (once, by you) with the needed permissions (contents:write, pull_requests:write, issues:write — fleet-audit publishes its ledger as an issue) and installed on the target repo.
  2. The App’s private key is imported into a GCP KMS asymmetric signing key (keyring github-token-minter-keyring, key github-token-minter-key, created by the github-minter Terraform module) — the raw key material never lives outside KMS.
  3. When submit-suggestion needs a token, the credential broker calls Minty (default endpoint http://github-token-minter.kubeagents-system.svc.cluster.local:8080/token) using the agent’s Workload Identity.
  4. Minty asks KMS to sign a JWT with the imported private key.
  5. Minty exchanges the JWT with GitHub for a short-lived installation token scoped to the target repository.
  6. Minty returns the token to the caller.

Recovery

Section titled “Recovery”

The agent does not refresh GitHub credentials itself. The git in its sandbox holds no credential and has no transport to a forge, so a remote git command fails by design rather than with an auth error, and SOUL.md §3 tells the agent to reach the repository through the version-control skill’s verbs instead. The credential broker refreshes its token from Minty before every credentialed call those verbs make. For other blockers, the recovery ladder (§4) caps retries at 5 iterations or ~10 minutes per distinct blocker before escalating.

Complementary integrations

Section titled “Complementary integrations”

Alongside GitHub PR flows, the persona explicitly names other declarative pipelines it will use when they’re the active workflow:

  • Config Connector — for GCP resources modeled as Kubernetes CRs.
  • ArgoCD / Flux — inspecting RootSync state and Application health as part of diagnostics.
  • GKE Hub fleet membership / Connect Gateway — for multi-cluster targeting.

SOUL.md §4 requires the agent to inspect these before manual intervention.

Anti-patterns

Section titled “Anti-patterns”

Explicitly called out as forbidden in SOUL.md:

  • Running raw kubectl apply against a live cluster for infrastructure changes.
  • Configuring git credential helpers manually.
  • Running ad-hoc git clone against the GitOps repo for change submission, or driving git/gh directly to open a PR or file an issue. SOUL.md §3.2 names exactly two packaged skills that may own the write path: submit-suggestion for a one-off change, fleet-audit for a scheduled audit run.
  • Outputting raw tool schemas, JSON payloads, or exit codes in user-facing messages.
