Autonomous watchdogs

agents/platform/cron/jobs.json defines the governance watchdogs. Each one carries a pre-authored prompt that runs on the Platform Agent on a cron schedule. The prompts typically point at a governance SOP; the agent reads the SOP, executes the procedure, and publishes what it found to your GitOps repo — an audit ledger issue via fleet-audit, plus a proposed PR via submit-suggestion where the fix is mergeable. The ledger issue is the record, and it is where a scheduled run is meant to be read; chat usually gets a one-line report linking to it, which in Slack with KAGE_SLACK_UX on arrives as a headline (ChatOps → Proactive alerts). On an install with no GitOps repository configured, an audit still runs: it keeps its findings in the report store on the agent’s volume and its chat report is the summary itself: the most severe findings, one short line each, the rest counted by severity, and a line saying that no GitOps repository is connected.

Watchdog runs execute autonomously: the agent config sets approvals.cron_mode: approve (see deploy/shared/defaults/config.yaml), so commands that would otherwise require human approval run without prompting when triggered by a scheduled job.

That waives the prompt, not the scan. Every command a scheduled run issues is still put through the Tirith content scan, and a finding refuses that one command — the run carries on and can take another route. The refusal reaches the agent as an ordinary denial string and the gateway logs it (Cron Tirith block: …); it is not written to the execution ledger, and it reaches the job’s saved output only if the run’s final response mentions it. The distinction matters because the threats Tirith looks for are the ones an unattended run is least able to notice: a run that reads text written by someone outside your organisation — an issue body, a log line, a tool result — can be talked into typing a homograph URL that matches no dangerous-command pattern at all. The scan also catches the shapes the pattern layer does know — curl | sh, base64-to-shell — which matters because approve is precisely the instruction not to block on those. A companion risk gate closes the two evasions Tirith does not inspect: pure-ASCII lookalike TLDs mimicking trusted infrastructure apexes (such as kubernetes.io.evil-cdn.co) and raw terminal escape or C0/C1 control sequence injection (_ESC), while unconditionally refusing execute_code in cron runs. Jobs declare an explicit risk tier: for agentic jobs, high (as well as unannotated runs defaulting fail-closed to high) applies a fail-closed read-only command policy (cron_command_policy_block), requiring every command segment to be an allowlisted inspection command while refusing mutating, unknown, or unanalyzable commands; low risk retains the configured cron_mode (denylist-only floor). A job that files a kanban card hands the work on to a worker, and a worker is not a cron session — but that does not put the worker outside the scan. It is spawned as a hermes chat -q subprocess, which marks itself interactive, so its commands meet the same Tirith scan on the interactive branch of the same gate; with no terminal attached, the approval prompt that branch would otherwise raise defaults to a refusal, which makes a worker stricter than the cron run that filed its card rather than looser. approvals.cron_scan: false opts a profile out of the Tirith content scan only; the execute_code block, terminal escape injection check, lookalike domain rejection, and the read-only policy remain unconditional. Regardless of settings, the hardline floor (rm -rf /, mkfs, fork bombs, and nine more), the sudo-stdin guard, and any approvals.deny globs still apply.

Both rosters are annotated on Reference → Cron jobs, which also covers the plumbing jobs on the Planning Agent’s: the named-profile cron ticker described in What fires the schedule, Cluster Agent reconciliation, and oobe, which runs first-run onboarding and four of the audits below and then the upgrade retrospective once, one after another, as soon as the first inventory scan settles, instead of leaving them to their schedules. The Platform Agent’s roster carries non-governance entries of its own: the github-repo-watcher poller, the k8s-event-watcher daily recap, the findings-queue nudge, the kanban workspace collector, kanban-board-health, which names cards stuck in blocked in chat, chat-delivery-watch, which reports a scheduled report that stopped reaching chat on a GitHub ledger issue and in Cloud Logging, stall-watch, which sweeps the namespaces of every running or reconciling cluster that has a Cluster Agent for controllers that stopped reconciling and raises an alert per namespace with a new stall, at most three a tick (the cluster’s Cluster Agent triages it in the alert’s thread, and the watch posts one line of its own when the stall clears), upgrade-readiness-watch, which produces the upgrade readiness report once when a cluster’s release channel offers a version it is below and again every week while it still is, upgrade-readiness-weekly-review and upgrade-readiness-weekly-brief, the Saturday pair that grades every cluster, registers each blocker and risk on the findings queue and composes the week’s brief, sa-role-watch, which says in chat when the agent’s Google service account holds a role beyond the read-only set, and feedback-prompt, which asks the operator for feedback once.

How a watchdog fires

Section titled “How a watchdog fires”

The schedule sits on the profile that does the work, but what advances it lives elsewhere, and that is worth knowing before reading the roster.

Cron ticking is a property of a running gateway, and gateways are per profile. Only the default (Planning Agent) profile has one — the Platform Agent is reached through the kanban dispatcher, which spawns a worker per card and exits — so the gateway’s own ticker never opens a schedule sitting in the Platform Agent’s roster. What does open it is profile-cron-tick, a job on the one store that is ticked, which runs hermes cron tick against every named profile with work due, once a minute. (Which profile has the gateway is what the experimental platformFrontDoor flag changes, and the ticked roster moves with it; that page carries the consequences.)

The result is an ordinary cron run in a hermes cron tick process of its own — one per tick, shared by any jobs due in the same minute — homed at the Platform Agent’s profile, taking that profile’s persona and toolsets (unless the entry’s enabled_toolsets replaces them) and the entry’s own skills, model and max_turns, and travelling the same execute → save → deliver → mark path a hand-run hermes cron tick takes. Four consequences worth knowing:

  • It is not a kanban card, and there is nothing to complete. The run has no card, no worker and no board history. Its outcome lands in the Platform Agent’s own execution ledger — cronjob(action='runs'), or cronjob(action='history') for one job — and its report is delivered per the entry’s deliver.
  • The entry’s own settings apply. skills are force-loaded ahead of the first turn, and a per-job model and max_turns are honoured: the ten audits carry max_turns: 250, and a job without one runs under the profile’s agent.max_turns, 150 for the Platform Agent, the budget its kanban workers run with. None of the shipped jobs pins a model.
  • A job will not run concurrently with itself. A tick takes cron/.job-<id>.lock for the length of a run, so a schedule that fires while its last run is still going is skipped rather than doubled. The skip is recorded: the ledger carries a skipped status alongside completed, failed and unknown, with a reason naming which of the seven causes applied — the job was already running here, already running in another process, the interpreter was shutting down, the dispatch claim was refused, the execution record could not be written before dispatch, the fire claim could not be taken at execution time, or the window was missed outright while the agent was down. A missed_window row’s error text also names how many occurrences went by, where that is computable. See Overlap and backlog.
  • One roster, not two. No governance id may also appear on the Planning Agent’s roster. Both would fire on their own schedules against the same audit, each writing the same ledger issue.

The shipping jobs

Section titled “The shipping jobs”

The rosters, with exact cron expressions, enabled state, and prompts, are generated from the two jobs.json files on Reference → Cron jobs. Ten governance jobs ship, all enabled on the Platform Agent’s roster — the fleet audits below. Further entries share that roster without being watchdogs. All but upgrade-readiness-weekly-brief are no_agent scripts that run no model: github-repo-watcher, a poller described under Pollers file cards; eod-event-watcher-daily-report, a weekday script that renders the k8s-event-watcher recap from the session ledger; findings-morning-nudge, an hourly script that adds findings from the findings queue to chat at a daily pace, holds new ones back while a non-critical finding it named is undecided, and once a day repeats up to FINDINGS_DAILY_CRITICALS (2 by default) undecided criticals and names any non-critical finding holding new ones back (Reference → Cron jobs has the pace and the settings that change it); kanban-workspace-gc, which collects finished workers’ workspaces, removes a sandbox cluster profile home the agent pod no longer has a profile for, and logs any unexpected top-level entries in the sandbox’s profile homes; kanban-board-health, which names any kanban card blocked for more than a day, listed newest first with its kind, reason and footer commands to move it (grouped when titles repeat), once a day until someone acts, because a worker’s or operator’s block is sticky by design and a card nobody was told about would otherwise wait forever; chat-delivery-watch, which keeps a per-job count of scheduled reports that failed to reach chat and, past a threshold, opens a GitHub ledger issue and writes an ALERT line that fluent-bit ships to Cloud Logging, the two channels that still work when chat does not (the relay design explains why it uses neither chat nor a PlatformAgent condition yet); stall-watch, which every half hour runs the Cluster Agent’s stall_report.py over the non-system namespaces of every running or reconciling cluster that has a Cluster Agent, keeps a ledger, and on a new stall (the CR’s spec.harness.stallWatch can exclude namespaces, hold young stalls and change the kinds scanned) sends the Session KV server a controller-stall inject per namespace, at most three a tick, the route the event watcher and the drift detector use: the alert is posted, that cluster’s Cluster Agent runs gke-stall-detection and reports in the alert’s thread with fixes a reply of “apply” can authorize, and the watch adds one chat line when a stall clears; upgrade-readiness-watch, which once a day reads the version each cluster’s release channel offers and, when a cluster is below a version the watch has not reported or reported more than a week ago, runs the fleet-upgrade-verification readiness report, saves it on the gateway pod and posts one line with the blocked clusters; sa-role-watch, which every hour reads the IAM policy of the management project and of each project in spec.scope and names, when it appears, once a day while it is held, and when it goes, any role bound to the agent’s Google service account (the one the agent’s ServiceAccount names for Workload Identity, and the credential broker’s own when federation is armed) that the read-only permission set does not carry, since a role granted after install would otherwise go unnoticed; and feedback-prompt, which posts one feedback request in the home channel a week after its first tick, at most once per install, with FEEDBACK_PROMPT_ENABLED and FEEDBACK_PROMPT_DELAY in the chart value platformAgent.deployment.env as its per-install switch and delay (Reference → Cron jobs describes the message, the two markers behind “once”, and how to set the two variables so that a chart apply keeps them). The Saturday pair for upgrade readiness is upgrade-readiness-weekly-review, one more no_agent script, which grades every cluster in scope and registers each blocker and risk on the findings queue, and upgrade-readiness-weekly-brief, the exception: a prompt job an hour later that composes the week’s brief from that review and the queue under its own SOP, a model turn that is not an audit and is not counted among the audits below.

The ten fleet audits

Section titled “The ten fleet audits”

Each audit reads its SOP, executes read-only checks against the fleet, writes a validated findings file, and hands it to the fleet-audit skill’s audit_report.py helper. The helper owns every forge call, through the version-control broker, and renders every body itself — the model never writes one.

Job SOP Audits
compliance-audit compliance_audit_sop.md Security and RBAC posture across the fleet
obtainability-audit obtainability_audit_sop.md Workload reliability: requests, PDBs, HPAs, probes, scheduling rigidity
security-patch-orchestrator security_patch_orchestrator_sop.md Version currency and upgrade-policy hygiene against what GKE offers at the cluster’s location, and whether a lagging cluster’s upgrade would go through cleanly
fleet-wide-cost-analysis fleet_wide_cost_analysis_sop.md Observable waste, in resource units — no billing export required
fleet-consistency-drift fleet_consistency_drift_sop.md Clusters diverging from a baseline derived from the fleet itself
ai-security-audit ai_security_audit_sop.md AI inference and training workloads: exposure, model provenance, weights
stockout-prevention stockout_prevention_sop.md Capacity obtainability, ComputeClass resilience, and single-zone stockouts
gcp-networking-fabric-audit gcp_networking_fabric_sop.md GCP networking fabric: subnet IP exhaustion, Cloud NAT, PSC, MTU, Cloud Armor, open firewalls
gce-compute-fleet-audit gce_compute_fleet_sop.md GCE startup-script failures, stalled MIG convergence, sole-tenant headroom, orphaned snapshots
upgrade-retrospective upgrade_retrospective_sop.md What the weekend’s GKE upgrades broke, classified against the upgrade failure catalogue

upgrade-retrospective differs from the streams beside it in two ways: it runs on Sunday evening over the clusters new to it or upgraded since its last run (its first run is a baseline of every cluster), writing its report to the shell sandbox’s volume (/opt/data/upgrade-retrospective/reports/upgrade-retro-report.md, the latest link) and posting what finish renders, a headline with the fleet’s finding and cluster counts and the most severe findings by object (the per-cluster lines are in the report), and it never opens a remediation pull request, since every finding it files is a manual recommendation a user can turn into one by asking. The same report answers “how did our upgrades go” when asked.

Two properties matter more than the check lists:

  • One ledger issue per audit, plus fixes on demand. The helper finds the audit’s existing open issue by its audit:<id> label and rewrites it in place, commenting only on what changed since the last run. A daily audit therefore produces one issue that stays current, not thirty near-identical PRs a month. A finding whose fix is a manifest is promoted into its own narrow pull request — automatically when it is critical or one of a few additive major fixes, otherwise when a repo writer asks for it on the ledger. See Declarative workflow.
  • Silence is a real outcome, but it has to be earned. A clean run that resolved nothing closes the audit’s ledger issue and returns [SILENT], so a quiet fleet sends no chat traffic. finish decides this, not the agent: silent_ok is true only when nothing is new, nothing is resolved, no remediation pull request opened or closed, and no coverage gap is new or changed. A run that could not read part of the fleet speaks the first time it sees a gap and each time the gaps change: it leaves the ledger open and names the gaps, because “I found nothing” and “I could not look” must not arrive as the same silence. Later runs with the same gaps stay silent, unless a finding the last run listed is no longer reported: then the run says how many, links the ledger, and does not call them resolved. A run that came back clean after carrying findings reports what closed, because a fleet that just got fixed is the one piece of good news these watchdogs produce. §7.4 of the ledger design says how gaps are compared and where their sentences come from, §7.5 has the full rule, and ChatOps shows what the channel gets.
  • Asking for a run cancels the silence. silent_ok answers “would a channel want this?”, and it cannot see that a person is waiting. So a job asked for on demand always reports its outcome and its ledger issue URL, whatever the flag says. The Platform Agent does not re-enact the audit in the session that took the request — several audits crammed into one turn share one turn budget and produce findings no kubectl backed. It marks the job due instead, with HERMES_HOME=/opt/data/profiles/platform hermes cron run <job-id>, and the next profile-cron-tick picks it up within the minute and runs it through the identical path the schedule uses. cronjob(action='run') is the trap to avoid: where the session cannot take a detached result — a one-shot hermes -z, a stateless HTTP turn, a Kanban worker, a nested cron run — or where the dispatch pool is full, it executes the job synchronously inside the calling session, which is the re-enactment this exists to prevent. Everywhere else it hands the run to the background delegation executor and returns a handle instead; that is closer to the tick’s behaviour, but only hermes cron run behaves the same way on every runtime and in a fresh process, so it stays the instruction. What the agent cannot currently do is issue it: hermes and the profile tree are on the gateway pod, every command the agent runs executes in the shell sandbox, and nothing bridges the two — so an on-demand run is unavailable until the deferral in docs/designs/agent-shell-sandboxing.md is settled. Ask for one and the agent says so; the schedule is unaffected. An operator with cluster access can still issue it directly against the gateway pod. The one run that does happen in a session is a card that delegates a single named stream per its SOP: that worker runs the stream itself, audit_report.py start to finish, and start refuses while another run of the same stream is in flight, so two such workers cannot scrub each other’s documents. Several streams asked for at once still queue.

Pollers file cards; watchdogs deliver reports

Section titled “Pollers file cards; watchdogs deliver reports”

github-repo-watcher shares the Platform Agent’s roster but is a different kind of entry. It runs github_scan_gate.py as a no_agent subprocess every ten minutes, sweeping the target repositories for work — today, unaddressed open issues on GitHub and unanswered review requests on the agent’s own pull requests on every declared forge, GitHub or Gitea. Almost every tick finds nothing, prints nothing, and costs no tokens at all. On the rare tick that does find something, it files a kanban card assigned to the Platform Agent, and the model wakes up then. One poll covers both sweeps, which is the reason they were consolidated: two jobs would be two credentials’ worth of API traffic and two chances to spend a turn on nothing.

That inversion is the point: a prompt job spends model turns — persona, skill, and a deterministic API call — to be told “nothing to do” almost every time. The trade-off is that a card is not a cron run: the roster’s skills, model and deliver do not reach the work the card produces. The Tirith scan does reach it, by the other route described above. That is acceptable for a poller, whose product goes to GitHub rather than to a chat channel, and unacceptable for a watchdog, whose product is the delivery — which is why the audit watchdogs are prompt jobs and stay that way. agents/platform/cron/README.md holds the full argument.

deliver: "chat" still matters for the gate itself: a sweep that cannot reach the forge prints one ⚠️ line and that line has to be audible. A sweep can be turned off without touching the roster by setting GITHUB_WATCHER_SWEEPS to the comma-separated list you want; unset means all of them. The pull-request sweep carries three further bounds of its own — a per-tick cap, a total refusal budget per pull request, and a bot allowlist — because its input arrives from a thread anyone can write in, where the issues sweep’s does not. All three are PR_AGENT_-prefixed environment variables, and docs/designs/pr-comment-conversation.md gives their defaults and the reasoning for each.

The retired jobs

Section titled “The retired jobs”

github-issue-resolver was a prompt job on this roster until github-repo-watcher replaced it. Its skill is unchanged and still does the triage — only the trigger moved.

Five watchdogs — blueprint-sync, policy-propagation, global-capacity-orchestrator, standardization-validator, and lifecycle-deprecation-manager — shipped disabled for several releases and are now gone from the roster entirely. As written none could produce a finding on a stock install: two compared clusters against a “master blueprint” document no install provides, one read policy templates from an unshipped /opt/defaults/templates/, one ran hourly with no defined output artifact, and one overlapped security-patch-orchestrator.

Their SOPs are gone from agents/platform/governance/ too; git history has them. Reviving one means writing a SOP against something a stock install actually has and then adding the job — see Adding a watchdog. Re-adding the entry alone will not help; the SOP is why they were retired. How a retirement is sequenced across releases is in agents/platform/cron/README.md.

Deleting the entries is not the whole of the second step either. The same silence that makes the merge safe makes it forgetful: an entry the volume holds and the image no longer mentions can never again be re-enabled, disabled, or removed, and cronjob(action='list') reports it forever. So a deletion has to be paired with retire_cron_jobs — profile_scaffold.py, exposed as the entrypoint’s --cron-retire, which runs after the merge and deletes the named ids from the store outright. The Platform Agent’s force-sync names these five and github-issue-resolver; the Planning Agent’s names the seven governance ids that once ran on its roster and github-issue-resolver, which had to stop firing there the moment they resumed firing on the Platform Agent’s roster, plus first-run-quick-value-audit, whose work oobe does; the two GCP audits added later never lived there and are on neither list. Both lists are hand-maintained and load-bearing: for as long as an id is on one it cannot be scheduled on that profile at all, because the deletion outranks anything the image ships, and taking a name off strands whatever copies remain.

What fires the schedule

Section titled “What fires the schedule”

Hermes’ cron ticker is a thread inside hermes gateway run, and everything it touches — the job store, the execution ledger, the tick lock — resolves from that process’s HERMES_HOME. It never enumerates profiles. This image runs a single gateway, homed at /opt/data, so the only roster that thread ticks is the Planning Agent’s. The Platform Agent’s lives at /opt/data/profiles/platform/cron/jobs.json, which the thread never opens.

profile-cron-tick is what ticks it. It is a no_agent script job on the Planning Agent’s roster — the one store that does tick — and each minute it runs hermes cron tick as a subprocess against every named profile with work due. Every governance watchdog fires through it, as does anything an operator schedules on a named profile’s own store:

A watchdog therefore fires through the same execute → deliver → record path a manual hermes cron tick takes, with its own profile’s persona and toolsets and the entry’s max_turns. Three consequences worth knowing:

  • A minute is the floor, not the guarantee. A named profile’s schedule is only ever inspected as often as the dispatcher runs, so a cadence finer than * * * * * cannot be honoured there. The dispatcher is itself scheduled as * * * * * rather than as a one-minute interval, and deliberately: Hermes re-anchors an interval job to the moment the last run finished, while the gateway ticker sleeps a fixed sixty seconds after each tick returns — so the next due time always lands just past the next wake and a one-minute interval job quietly fires every two. A cron expression is immune, because the completion time is snapped up to the next wall-clock minute. What is left is narrower: a dispatch that actually ran a watchdog blocks for up to 45 seconds waiting on the subprocess, and that usually costs the minute after it, so roughly one dispatch in twenty is collapsed and it is almost always the minute following a watchdog run. Quiet minutes are on time. Treat every schedule below as accurate to about a minute, which is well inside the sweet spot in Adding a watchdog and does not constrain the shipping roster. Nothing here is latency-critical; if something ever is, it needs its own timer, not a finer cron expression.
  • Overlap and backlog are tick()’s problem, not the dispatcher’s. A tick takes an exclusive lock on the profile’s store (cron/.tick.lock) while it decides what is due and advances every due job’s next_run_at, then releases it once every due job has been dispatched rather than holding it until they finish — so an agent down for two days runs each missed daily audit once on return, not once per missed day. Overlap is held per job rather than per profile: a job takes cron/.job-<id>.lock for as long as it runs, so a second dispatch will not start the same job twice, but it will start a different one. That distinction matters here because each platform tick is a separate hermes cron tick process. Holding the profile lock across execution — the upstream default — would make a fleet audit block every other dispatch for its whole run.
  • A broken ticker is loud. Dispatches are silent on a quiet minute, but a tick that fails is recorded as a failed profile-cron-tick run with the subprocess output in <profile-home>/cron/tick.log — the one failure mode this job must not have is the silence it exists to end. Individual watchdog runs stay where every other run is: the profile’s own execution ledger, and cronjob(action='history'). That ledger is pruned per job rather than per board — 1000 rows each (MAX_TERMINAL_EXECUTIONS_PER_JOB), then a 5000-row sweep across the board that may never take a job’s newest 50, so the floor outranks the ceiling and the real bound is 5000 plus 50 per job id. The distinction is the difference between a usable history and none: pruning to the newest 1000 rows across all jobs let the minute-ly ticker evict a daily watchdog’s only row inside seventeen hours, so the history of the job you would actually go looking at was always empty.

Job shape

Section titled “Job shape”

Each job in jobs.json follows this schema:

  • id — stable identifier, referenced in observability and disable/enable ops. It outlives renames: obtainability-audit is now the Workload Reliability Audit, but the id stays put.
  • risk — declared risk tier ("low" or "high"). For agentic (prompt-driven) jobs, "high" applies a fail-closed read-only command policy requiring every command segment to be an allowlisted inspection command (kubectl get/describe/logs/top, gcloud … list/describe, read-only text utilities, --dry-run validations) and refusing mutations while the run continues. "low" retains the profile’s configured cron_mode (typically approve). Runtime-created jobs default to "low", legacy volume entries backfill to "low", and unannotated in-flight dispatches default fail-closed to "high". For no_agent: true jobs like github-repo-watcher, there is no agent loop and therefore no tool-approval surface to gate; "high" is an input-threat classification of untrusted input: repository events for github-repo-watcher, cluster event text for stall-watch, the budget and workload names upgrade-readiness-watch saves and the budget, pool, exclusion and webhook names upgrade-readiness-weekly-review registers; today the tier is metadata only for those jobs, and nothing isolates the subprocess at runtime.
  • schedule.expr — standard 5-field cron in the pod’s local time zone (UTC unless the pod’s TZ is overridden).
  • prompt — what the run is asked to do, copied verbatim into the turn. Governance jobs point at an SOP by its absolute path in the profile home (/opt/data/profiles/platform/governance/<sop>.md), since a cron run starts in a directory of its own under cron/runs/. The profile home’s governance/ is where profile_scaffold.py overlays the baked /opt/platform-template/governance/ directory. An absolute /opt/defaults/governance/... path does not resolve — nothing is mounted there. The ten audit prompts and the weekly brief’s also state how long their SOP is and which section holds the checks (the composing rules, for the brief), because a read that stops early lands in the preamble and the run reports a clean fleet it never inspected. What the prompts deliberately do not restate is the [SILENT] rule — each SOP’s closing section states it in full, qualifiers included, and a shorter version in the prompt would both lose the qualifiers and tell the run what its answer looks like before it decides what to check.
  • skills — the skills the work needs. The scheduler prepends each one’s content to the prompt, force-loading it ahead of the first turn rather than leaving the load to the model’s discretion. The audit watchdogs use fleet-audit.
  • max_turns — the run’s own tool-calling iteration budget, required on every model-run entry. The ten audits carry 250; the profile’s agent.max_turns (150 for the Platform Agent) is what a job without one, and every kanban worker, runs under: an audit asked for in chat runs as a kanban worker, so it gets the profile’s value, not its entry’s. A no_agent job must not carry it.
  • no_agent and script — a subprocess instead of an LLM turn, used by every job on the Planning Agent’s roster and by github-repo-watcher, the daily recap, the findings-queue nudge, the workspace collector, the board-health check, chat-delivery-watch, stall-watch, upgrade-readiness-watch, upgrade-readiness-weekly-review, sa-role-watch and the feedback prompt on the Platform Agent’s (script resolves in that profile’s scripts/, which for the Platform Agent is a link to the shared directory). The governance watchdogs omit both: they are model runs. On a prompt job script is a pre-run script instead: it runs before the turn and its output goes above the prompt. upgrade-readiness-weekly-brief is the only such job, and its enabled_toolsets replaces the profile’s toolsets (Reference → Cron jobs).
  • enabled — set to false to disable a job without deleting its entry.
  • deliver — where the run’s outcome goes: "all" sends it to every configured target, "chat" posts it as the job wrote it (for an audit watchdog, the report its finish step rendered for each repository, or a line saying the run, or one of its repositories, did not finish; for any job whose run failed, one plain line saying it didn’t run, why, and when it tries again or that an admin needs to fix it, posted once until the job runs again or fails for another reason) into a thread whose replies reach the Chat Agent with the report attached (see the relay design), and "local" resolves to no target at all and drops it. "chat" is one target among them, not an override, so "all" reaches it too. No governance job uses "local", so a watchdog that has stopped working is visible rather than indistinguishable from a quiet fleet; the one "local" entry is chat-delivery-watch, whose product is not a chat message. Which value each one carries is in agents/platform/cron/jobs.json.

Disabling a watchdog

Section titled “Disabling a watchdog”

Flip enabled to false in agents/platform/cron/jobs.json. The scheduler honours the flag directly: the job stops being due, and nothing runs.

Flip the flag; do not delete the entry. An id can be dropped from the roster only once no live cluster still needs the image to hold the job off, which is the path the five retired watchdogs took. Deleting is never the whole step: the same release must also name the id in the platform force-sync’s --cron-retire (deploy/shared/docker-entrypoint.sh), or the volume keeps a disabled entry no later image can reach.

The Platform Agent’s roster travels. That profile is scaffolded by profile_scaffold.py on every start-up, and its merge_cron_store merges the image’s roster over the volume’s unfiltered — the image wins every key it ships, the volume keeps every key it does not. So redeploying an entry with enabled: false switches it off on every existing cluster at the next pod restart, and a stale enabled copy cannot outlive the release that retired it. A job an operator added by hand survives, because the merge never prunes — unless its id is on the force-sync’s --cron-retire list, which is applied after the merge and deletes outright.

The Planning Agent’s roster travels too, by a different road. The Planning Agent is the default profile, which is not scaffolded: it lives at $HERMES_HOME directly, and the entrypoint reconciles the volume’s cron/jobs.json against the shipped roster by job id, per key, under the same rule — the image wins every key it ships, enabled among them, and a key it ships nothing for stays as the volume had it. A ledger of every id the entrypoint has ever installed keeps a job that was removed on purpose — the two onboarding jobs, once the first-run report has landed — from being reinstalled as though it were new. An install that finished onboarding before oobe shipped never gets that job either, so an upgrade does not start its first-run audits. agents/platform/cron/README.md has the entrypoint steps behind this.

Three consequences worth stating plainly:

  • A hand-added job still survives every upgrade. Neither step deletes an entry the image does not declare, and neither touches a key the image does not ship, so an operator’s own job and the scheduler’s own state both come through untouched.
  • A hand-edit on a live pod does not survive one. Editing enabled in $HERMES_HOME/cron/jobs.json on the PVC holds only until the next restart, which is precisely when the reconcile takes the image’s value back — silently, since reconciling a key to the image is the expected path and logs nothing job-specific. The image is the declaration of record; edit agents/chat/defaults/cron/jobs.json and roll. If you must stop a job before the next roll can ship, treat the PVC edit as a stopgap and land the image change behind it.
  • deliver is the one shipped key the runtime keeps. Onboarding rewrites it to origin on the delivery job, so taking the image’s value back would send the first-run report nowhere.

The cronjob tool is not a route to either roster: it is denied to the Planning Agent (agents/chat/config.yaml), and the Platform Agent’s copy addresses that profile’s own store, not this one.

Adding a watchdog

Section titled “Adding a watchdog”
  1. Write a governance SOP in agents/platform/governance/<your-sop>.md.
  2. Add a job entry to agents/platform/cron/jobs.json pointing at it as governance/<your-sop>.md. That is the Platform Agent’s own roster, fired by profile-cron-tick, so the run gets that profile’s persona and toolsets, and the entry’s skills and max_turns, which a model-run entry must carry. Do not also add the id to the Planning Agent’s roster, or the job runs twice.
  3. If the job files findings, add its id to the allowlist in agents/platform/skills/fleet-audit/scripts/audit_report.py and set "skills": ["fleet-audit"].
  4. Redeploy the agent image at the revision carrying the change (./upgrade.sh --upgrade-mode=harness --image-tag=<ref>). The entry lands on the next pod restart, on new and existing clusters alike — the Platform Agent’s roster is merged in full, so no PVC edit is needed. A job on the Planning Agent’s roster lands the same way; that roster is reconciled in full too.

The repository-side steps — regenerating the cron reference table and the fast rebuild path for a dev workspace — are in agents/platform/cron/README.md.

Keep the schedule realistic — LLM inference on every tick has cost. Hourly or daily is the sweet spot for most SOPs; sub-15-minute cadences should have a clear justification. Stagger start minutes so two audits never contend for the same session.

Budget the run as well as the schedule. Each model-run entry declares its own per-turn tool-calling budget, max_turns, which the image’s scheduler reads ahead of the profile’s agent.max_turns (the patch). The ten audits carry 250, the number three runs at 90 motivated; the profile’s own value is 150 and is what the kanban workers run under, so an audit’s headroom never reaches a delegated chat request. A run that exhausts its budget is stopped mid-flight and recorded as a timed_out event, which reads misleadingly: no clock expired, the agent simply took more steps than it was allotted, and raising any of the HERMES_*_TIMEOUT values will not help. The ten shipping audits finish well inside 250, but an SOP that gains checks and a fleet that gains clusters both spend against it; raise the entry’s number, not the profile’s.
